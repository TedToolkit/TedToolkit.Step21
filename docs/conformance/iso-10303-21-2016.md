# ISO 10303-21:2016 processor conformance statement

The machine-readable clause trace and Annex D PICS answers are in
[`iso-10303-21-2016.json`](iso-10303-21-2016.json). Its normative navigation source is the publicly available
[ISO/TC 184/SC4/WG11 Edition 3 final text](https://www.steptools.com/stds/step/IS_final_p21e3.html).

## Current claim

The library does not claim complete ISO 10303-21:2016 processor conformance. Syntactical classes 1 and 2,
all five Annex D string-encoding questions, clear-text/archive URI references, explicit schema populations,
signatures, multiple schemas, and UUID anchors have executable proof. Annex F ECMAScript binding is deliberately
outside the product boundary. The manifest keeps
class 3 unchecked because complete class 3 also requires operational EXPRESS constants. Entity, select, and
enumeration short-name read/write is checked when the schema-defining document supplies the mapping metadata.

Class selection is checked against both serialized facilities and transport context. In particular, an exchange
structure stored as the root of a ZIP containing additional files is rejected when it declares class 1 and is
accepted at class 2 or class 3.

The lexical proof also distinguishes stored presentation from effective values. Raw control octets are ignored
wherever they occur, including inside tokens, string directives, and comment delimiters; the clause 13 `\N\` and `\F\` print controls
likewise affect presentation only and do not materialize newline or form-feed characters in a decoded STRING.
Control characters that are part of the effective STRING value remain representable through the clause 6.4.3.4
`\X\hh` encoding.
Print controls are rejected throughout ANCHOR and REFERENCE sections, including when embedded in an anchor STRING
or BINARY; a doubled reverse solidus that merely produces the literal text `\N\` or `\F\` remains valid.

The remaining behaviors require ISO 10303-11 constant, evaluated-set, type and validation semantics that are absent from the
authorized Edition 2 files. Per the approved source policy they are `source-excluded`: the implementation does not
guess them, affected PICS answers remain false, and the overall full-conformance claim remains `blocked`. ISO21-005 and
ISO21-009 provide independently verified physical-name and source-described semantic profiles for everything the
available files do define.

## Annex D implementation limits

The default processor boundary permits 1,048,576 schemas, data sections, occurrence names, or aggregate elements
at the applicable bounded collection, and 128 nested aggregate/typed-value levels. INTEGER uses arbitrary-precision
`BigInteger`; REAL uses an exact finite decimal with arbitrary-precision significand and exponent. Both remain
bounded by the operation input/output and item quotas. A stored STRING is limited to 32,769 UTF-8 octets including
apostrophes. BINARY has no independent bit limit and remains bounded by the 67,108,864-character input and output
quotas. The JSON contract test binds these answers directly to `Part21ProcessingLimits.Default`.

## Interpretation

`implemented` means the row names production code and one executable primary proof. `not-applicable` covers
physical tape, diskette, record blocking, multi-volume media operations, ISO information-object registration, and
the deliberately excluded ECMAScript language binding. `source-excluded` means a required Part 11 definition is
absent from the authorized files; it is an explicit negative conformance answer, never an implicit partial claim or
permission to infer behavior.
